## A4: runs as shell under Shizuku

```
shell        11341     1 u:r:shell:s0      shizuku_server              shizuku_server
shell        11545     1 u:r:shell:s0      io.github.egoushka.tin:tin  io.github.egoushka.tin:tin
shell        11560 11545 u:r:shell:s0      tin                         tin serve
```

The phone was then unplugged and plugged back in: the same pid 11560 was still serving. After `kill` of the `tin`
child, the service started a new one (pid 13052) under the same parent within 7 s. After the file-mode fix,
`/data/local/tmp/tin` and `bin/` are `drwx------`, `bin/tin` is `-rwx------`, `policy.toml` and `tin.log` are
`-rw-------`, all owned by shell. (The first build left the binary `rwxrwxrwx` and the log `rw-rw-rw-`, because
Shizuku starts the service with umask 0.)

## A5: only adb can connect

```
as shell: 200
app uid: 10291
as app:   tin: connect: Permission denied (os error 13)
PASS A5: SELinux refused the app's connect before tin saw it
```

logcat:

```
avc:  denied  { connectto } for  path=0074696E scontext=u:r:runas_app:s0:c35,c257,c512,c768
tcontext=u:r:shell:s0 tclass=unix_stream_socket permissive=0 app=io.github.egoushka.tin
```

`0074696E` is `\0tin`, the abstract socket. The probe ran as the app (its own copy of the binary from the APK), so
the refusal is the kernel's, not a failure to execute. tin's own peer-uid check was therefore not reached on the
device; it stays as a second layer for systems whose SELinux policy is looser.

## A7, A8: latency

`uv run scripts/accept.py --bench 20`: Settings `getBatteryDeviceState`, phone unlocked, one uncounted warm-up per
path, nearest-rank percentiles (p95 of 20 is the 19th smallest). The bridge path is one MCP session (Python SDK
2.3.0) over `adb forward`; the raw path starts a new `adb shell` per call; the third row is the time tin logged for
each `cmd` it ran.

Run 1 (first APK):

| path | n | p50 ms | p95 ms | min | max | mean |
|---|---|---|---|---|---|---|
| bridge (MCP over adb forward) | 20 | 1501 | 1642 | 1340 | 1674 | 1491 |
| raw adb shell cmd | 20 | 1497 | 2055 | 1306 | 2215 | 1558 |
| cmd inside tin (from its log) | 20 | 1432 | 1565 | 1268 | 1590 | 1423 |

Run 2 (after the file-mode fix):

| path | n | p50 ms | p95 ms | min | max | mean |
|---|---|---|---|---|---|---|
| bridge (MCP over adb forward) | 20 | 1474 | 1538 | 1316 | 1604 | 1460 |
| raw adb shell cmd | 20 | 1467 | 1670 | 1364 | 1676 | 1494 |
| cmd inside tin (from its log) | 20 | 1398 | 1441 | 1247 | 1530 | 1377 |

A8 as the spec defines it (bridge p95 minus raw p95) is negative in both runs, because raw `adb shell` pays for a
new shell session each call. The bridge's own cost, bridge minus `cmd` inside tin, is 69 / 76 ms at p50 and
77 / 97 ms at p95: the Python client, the USB hop and HTTP parsing together.

Where the 1.4 s goes, timed on the phone with `date +%s%N` around 10 calls each:

| call | ms |
|---|---|
| `execute-app-function … getBatteryDeviceState` | 1262–1561 |
| `execute-app-function … noSuchFunction` (fails at once) | 89–129 |
| `cmd package path com.android.settings` (mean) | 58 |

So `cmd` plus the system service costs about 0.1 s, of which about 60 ms is starting `cmd`. A binder backend in
Kotlin could save at most that; the spec's stop condition (overhead p95 > 200 ms) is far from triggered.

The spec's earlier note that one raw call takes 0.29–0.54 s was most likely measured on failing calls: the session
that wrote it had not yet seen a successful result (it planned to learn the output format with the phone unlocked),
and a locked call on this run failed with code 1000 in 0.64 s end to end. A successful call takes 1.3–2.2 s.
